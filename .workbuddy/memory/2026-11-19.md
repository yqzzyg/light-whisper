# 2026-11-19

## 笔记多段录音：产品决策确定

用户明确回答两个问题：
- 「转录后找不到录音文件」= **笔记页看不到入口**（文件本身还在 `notes_audio/`，并非被清理）
- 一条笔记多次录音 = **保留多段**，不要覆盖

当前实现的问题（代码核实）：
- `note_recording_service::start` 每次生成 `note-{note_id}-{millis}.wav`，多段确实会各存一个文件；
- `set_audio_with_connection` 无条件 `UPDATE notes SET audio_file=?2`，第二次 stop 覆盖单槽引用，旧段当场变孤儿，重启 `cleanup_startup` 按 `audio_file_names()` 删除；
- `transcribe_note_recording` 幂等分支「transcript 非空直接返回」，所以转录后再录的新段**永远不会被转写**，笔记显示旧文字 + 新时长；
- `transcribe_note_recording` 写的历史行 `audio_file=NULL`（刻意不复制），而 `reveal_history_audio` 只认 `history_audio/` 目录，笔记页又没有回放/定位入口 → 三条路都找不到文件。

### 待落地方案（B：多段录音）

- `notes.sqlite3` schema 升到 `user_version=2`，新增 `note_recordings`（id / note_id FK CASCADE / audio_file / duration_sec / transcript / history_id / sort_order / created_at），索引 `(note_id, sort_order, id)`。单表而非 JSON 数组：需要按段查未转写、按段删、给 GC 提供引用集合。
  （**已于 2026-11-20 变更**：库文件并入 `minutes.sqlite3`，版本机制换成 `schema_meta(module, version)`；`notes.audio_file` 在 v3 删除。本条留作当时的设计记录。）
- 迁移：老 `notes.audio_file` 非空的行灌一条段记录；`notes.audio_file` 置 NULL 不再是事实源；`notes.transcript` 保留为段转录拼接的缓存；列表 `has_audio` 改 `EXISTS(note_recordings)`。
- 转录改为**段级幂等**：`transcribe_note_recording(note_id)` 顺序转所有 transcript 为空的段，每段一条 `history(mode="note", audio_file=NULL)`；成功写段 transcript/history_id，最后重算 notes.transcript（拼接）与 duration_sec（求和）。中途失败保留已完成段，重试跳过。仍不整段合并转写（要拼临时 WAV，违背零复制）。
- `audio_file_names()` 改读段表；删笔记 FK 级联 + 逐文件删；删段即删文件；`cancel` 仍只删当前半成品。
- 前端 `NoteDetail` 加 `recordings[]`；转录 tab 展示全文 + 分段列表（时长/状态/回放/定位/删除）；新增 `reveal_note_audio(recording_id)`（复用 history 的 explorer /select 模式）；P2 历史转存笔记无段，继续显示「录音在历史记录中」。

### 其他已识别缺口（未修）
- `RecordingBar` 只在 NotesPage 渲染，切到首页/历史时录音继续但无可见指示与停止入口。
- 停止录音时后端返回值 + `note-recording-state` 事件会触发两次 `refreshAfterStop`（重复拉取，无功能问题）。

**状态：方案已向用户呈现，等确认后开工。**

## 笔记编辑器换成所见即所得（TipTap 3）

### 选型结论（推翻原「不引入 tiptap」决策）
- 选 **TipTap 3 + `tiptap-markdown`**，不用 Milkdown Crepe。实测（最小页面 vite build、临时目录装完删掉）：Crepe 全量 1,011 KB gzip / 216 包 / 带 Vue 运行时 10 个包 + CodeMirror 6 33 包；TipTap 265 KB / 77 包 / 0 Vue；Milkdown 只用 core + preset 自拼是 209 KB / 0 Vue，但**不带任何 UI**（工具栏、slash、表格操作全自写），工作量与 TipTap 相同、生态更弱。
- Crepe 的 UI 是 Vue 写的（`defineComponent` + `h()`），官方文档 Tech Stack 完全没提 Vue —— 只读文档发现不了。
- 记录在 `docs/neo/notes-feature-plan.md` §7.1（决策 10–14）与 §1/§3.4/§5。

### 实现要点（改回会坏）
- 三态：`MarkdownEditor` = 所见即所得（默认）/ 源码 textarea / 只读预览，同一时刻只挂一个。
- `NoteEditor` 里 `<MarkdownEditor key={note.id}>`：换笔记**必须重建编辑器**，否则撤销栈跨笔记生效，Ctrl+Z 能把上一篇内容盖回来并自动保存。
- 受控同步（`RichTextEditor`）：`onUpdate` 序列化后写 `serializedRef` 并上抛；`useEffect` 里只有 `value !== serializedRef` 才 `setContent`，写完把选区夹到新文档长度内。空串回声直接跳过。
- 排版复用 `.markdown-content`：**`markdown.css` 的 import 从 `MarkdownContent.tsx` 移到 `main.tsx`**（原来它在懒加载 chunk 里，编辑器首次打开会没有排版）。katex CSS 仍留在 `MarkdownContent.tsx`。
- `markdown.css` 给 `.markdown-content` 设了 `white-space: normal`、`table { width: max-content }`，编辑器要覆写必须用双类名 `.notes-rt-content.markdown-content`（同特异性时后加载者赢）。
- `Markdown.configure({ breaks: true })`：只读渲染给 `p` 加了 `white-space: pre-wrap`，软换行本来是看得见的；不开 breaks 会被折成空格（用户换行凭空消失）。代价是源码态里看到行尾 `\`。
- `TableEnterGuard`（priority 100）：表格里 Enter / Shift-Enter = `addRowAfter`。**不能让它拆段落**：`tiptap-markdown` 的表格序列化遇到多段落单元格会输出 `[table]`，整张表内容消失（已实测）。
- 工具栏 `NoteEditorToolbar` 用 `useEditorState` 只订阅必要状态；按钮 `onMouseDown` 必须 `preventDefault`，否则点击先清掉选区、格式落不到选中文字上。
- `buildNoteExtensions()` 单独导出给测试用（测试另抄一份扩展列表，会随配置变化悄悄失效）。

### 体积预算重定（`scripts/check_bundle_budget.mjs`）
- 新增 `notes_gzip_bytes`（`NotesPage-*` chunk，现 255 KB / 限 300 KB），并从 `core_js_gzip_bytes` 里扣除；core 现 198 KB / 限 210 KB。
- `total_js_gzip_bytes` 340 KB → 620 KB（现 586 KB）；`total_dist_bytes` 2.5 MB → 3.4 MB（现 3.12 MB）。

## P4 AI 摘要实现（2026-11-19）

### 结构
- 新增 `services/note_summary_service.rs`：素材拼装（标题 + 手写正文 + 转录）→ `split_parts`（段落优先，超预算退到句末，仍超硬切）→ 逐块要点 → 合并成稿。
- 新增 `commands/note_summary.rs`：`generate_note_summary(note_id)` / `cancel_note_summary()`。
- 数据层 `notes_service::set_note_summary`（**不改 `updated_at`**，摘要时间记 `summary_generated_at`）。
- `NoteDetail` 新增 `summary_stale`：`detail_from_row` 用 FNV-1a 比对「转录 + 正文」指纹，算法只在 Rust 一处。
- 前端 `hooks/noteSummaryStore.ts`（模块级，切页不丢）+ 摘要 tab（生成 / 取消 / 重新生成 / 复制 / 过期提示）。

### 改回会坏的决策
- **短素材（只有一块）跳过「先摘要再摘要」**，直接出终稿；否则白白多一次往返。
- **流式只在最后一次调用开启**；前面每块非流式，进度靠 `note-summary-status` 的 `part i/n`。
- **取消只能块间生效**：`send_llm_request` 中途无法打断，正在飞的那次返回后才停；不写半截摘要。
- **失败/取消保留旧摘要**：只有成功拿到非空摘要才写库。
- **并发与转写分开**：`AppState.note_summary` 独立占位，转写跑着也能给另一篇生成摘要。
- **事件 payload 不一致**：我们自己发的状态带 `noteId`；`llm_client` 的流式 chunk 只带 `sessionId`（我们传 None），所以前端 `streaming` 分支**不能按 noteId 过滤**，否则预览全是空的。靠「同一时刻只有一个摘要任务」兜住。
- 取消判定用**精确文案** `"已取消生成"`（命令层与 store 各写一份常量），不要用 `includes("取消")`——网络层「请求已取消」会被误吞。
