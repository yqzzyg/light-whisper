方案文档：`docs/neo/unified-transcription-service-plan.md`（已实施，第 9 节记了落地时对设计的三处收敛）。

**背景**：上传音频走原生流式、笔记录音走整段路径直传，两条链路各自拿锁、各自判引擎、

真正根因是音频增强器（`reuse_enhancement.py`），与链路结构无关，本次没动它。

### 结构变化

- 唯一入口 `transcription_service::transcribe(app, state, AudioInput, TranscribeOptions)`，
  三种策略：`Whole` / `Streaming` / `Chunked`；在线引擎在入口先分流到 `dispatch_online`。
- `AudioInput` 只有 `WavBytes(&[u8])` 与 `File(&Path)` 两个变体（借用，不拷字节）。
- `Preview` 是「要发什么进度」的意图枚举：`None` / `ImportInterim` / `ChunkProgress{note_id, recording_id}`。
  事件名、payload、负数 sessionId 全在 `services/transcription_events.rs`。
- `funasr_service` 补了 `transcribe_locked` / `transcribe_path_locked` / `transcribe_pcm16_locked`；
  `transcribe` / `transcribe_pcm16` 保留薄壳给实时听写，`transcribe_path` 无调用方已删。
- 新增 `audio_service::wav::wav_pcm16_samples`：流式既能吃文件也能吃 WAV 字节，
  上传因此不必为了喂样本再落一份临时文件。

### 一个容易踩的坑（改回去会坏）

`transcribe` 里 **先 `plan_transcription` 再拿 `native_asr_owner` 锁**，不是相反。
流式要先解码成 PCM，解码耗时几百毫秒到几秒；如果放在持锁之后，
同时触发的热键录音会被一次 mp3 解码堵在锁外。`Plan` 枚举就是为了把
「策略 + 它需要的数据」一次算好，避免出现「策略对了但样本没准备」的半成品状态。

### 两段式上传

`probe_audio_file(path) -> AudioProbe`（camelCase）：只读 symphonia 容器头拿 `n_frames`，
不解码样本；拿不到时长就返回 `None`，前端显示「时长未知」而不是退回全解码。
上限判断按「16k 单声道 16bit ≈ 32000 字节/秒」估算 WAV 体积，比源文件大小准。

前端 `audioImportStore` 状态机：`idle → picked(path, probe) → transcribing → done`，
新增 `selectAudio` / `startImport` / `cancelSelection`（原 `importAudio` 已拆掉）。
转写失败时**保留 picked**，同一份文件可直接重试。

### 更正：长录音不能改流式（用户指出，属实）

用户提醒「笔记用整段是 R7000P 时期为了解决大长录音内存/显存溢出」。核实：
提交 `3168656`「整段转写在本地引擎 `finish` 时要拼全部 PCM，内存随时长线性增长」、
2026-11-20 日志「整段交给本地引擎时 Python 端要把整个 WAV 读进内存」、
`MEMORY.md` 原约定「笔记转写必须直传路径」。

所以「笔记改流式更快」这条建议在内存维度上是倒退（1 小时）：

| 方案 | Rust 侧 | Python 侧 | 峰值 |
|---|---|---|---:|
| 整段（现状，路径直传） | 无样本 | int16→float32 230MB | ~350MB |
| 流式（不推荐） | `Vec<i16>` 115MB | `_chunks` 230MB + `concatenate` 再一份 | ~575MB |
| 切片 10 分钟块 | 无 | 单块 float32 38MB | ~40MB |

排查中还否掉了两个猜测：VAD 在 317 秒上只要 1.4–1.9s，不是整段慢的原因；
`_cleanup_memory` 只是 `gc.collect()`。代码层面整段与流式 `finish` 都是单次
`session.run`（超 115 秒走 `audio_chunk_mode=auto`，内部分 30 秒块），
所以 81s vs 47s 的差异来自运行时资源状态而非推理组织方式——这也与「整段吃资源」吻合。

正确方向：把切片从「>2 小时兜底」变成常态——阈值降到 10 分钟、块 5–10 分钟、
预算系数 `dur/10+120` → `dur/3+120`。流式只留给上传页预览。
已同步 `docs/neo/unified-transcription-service-plan.md` §10 与 `MEMORY.md` 约定。

## 上传改为与笔记同一条路（方案二）

用户确认「没有渐进文字也行」，于是把上传的 `Streaming` 策略整体删掉，改为
`import_audio_to_wav → save_audio(先落盘) → AudioInput::File → Whole/Chunked`。

- 落盘排到转写前：音频本来就要存历史文件，提前写让转录层能路径直传，Rust 侧不再留整段 WAV。
  代价是落盘成了前置条件，失败直接报错（不再像以前静默丢音频）。
- 新增 `history_service::audio_path` + `discard_audio`：失败回滚，维持「失败记录不占音频文件」。
- `Strategy` 与 `Plan` 合并成单个 `Plan { Whole, Chunked(&Path) }`，`pick_strategy` 改名
  `plan_transcription`——只剩两条路且一一对应，两层枚举是空抽象。
- 删 `transcription_events::InterimChannel` / `Preview::ImportInterim` / 负数 sessionId /
  `wav_pcm16_samples`；前端删 interim 订阅与 `interimText`。`NativeStreamClient` 保留（实时听写用）。

顺带修了一个既有缺陷：`transcribe_whole` 缺 `require_success`，引擎失败时返回
`Ok(success=false)` 会被当成「成功 + 空文本」记进历史，失败回滚也不会触发。
历史重识别因此从「这条记录没有可重新处理的文本」变成拿到引擎真实错误。

验证：Rust 992、vitest 1059、tsc/eslint/vite build/check_bundle/check_formal/check_doc_refs 全过；
clippy 8 条均为既有基线。**端到端未跑**——上传的真实落盘→转写→失败清理路径没有自动化覆盖，
需要在 app 内上传一次确认（317 秒素材仍在 `Downloads\note-6-1795098340882.wav`）。
