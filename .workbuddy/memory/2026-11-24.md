## 说话人分离方案文档（docs/neo/speaker-diarization-plan.md）

产出 `docs/neo/speaker-diarization-plan.md`（645 行），面向**面对面会议、单麦克风混音**场景。

核心结论：
- 声纹模型选 3D-Speaker CAM++ ONNX（`3dspeaker_speech_campplus_sv_zh_en_16k-common_advanced.onnx`，
  出自 sherpa-onnx release），约 27MB，运行时下载（不随包内置）。
- 分段不引 pyannote：用 FireRedVAD 粗分段 + 段内声纹变化点细分（1.5s 窗 / 0.75s 步长）。
- 聚类纯 numpy average-linkage 层次聚类，**不能用 sklearn**（在 build_engine.py 排除列表里）。
- 只在本地引擎做，P0 只做 Qwen3；在线引擎（GLM/DashScope）明确不支持。
- 分离是旁路：模型缺失/异常一律降级为现有整段转写，服务层收敛，命令层无感知。

关键代码事实（写文档时核实）：
- 本项目只有麦克风采集，`windows_capture.rs` 无 Render 方向 → 永远单轨混音。
- `note_recordings.transcript` 是纯 string，**全链路无分段结构** → 这是最大改造点，不是加字段。
- `qwen3_asr_server.py` 的 `_filter_speech` 把 VAD 段合并成首尾区间，VAD 分段能力被主动丢弃。
- `firered_vad.py` 的 fbank（16k/25ms/10ms/80维/dither=0）与 CAM++ 输入要求一致，
  唯一差异是归一化：CAM++ 要**逐句均值归一化**，不是固定 CMVN。不做则嵌入塌成一团。
- `server_common.py` 的 `_execute_action` 是字符串分派，加 `transcribe_diarized` 是纯增量。

## 重要修正：分段器改为 pyannote（2026-11-24 二次修订）

初稿判「不引入 pyannote」，理由逐条核实后**全部不成立**，已改文档：

| 初稿理由 | 实际 |
|---|---|
| HF gated 要 token | 许可是 **MIT**；gating 只收联系信息；**sherpa-onnx 在 GitHub release 分发非 gated ONNX**，openwhispr 用的就是它 |
| 需外部二进制 | 我们用 onnxruntime 直跑 ONNX，同进程、无 torch（openwhispr 用二进制是为跑完整 pipeline） |
| 体积大 | 实测 **5.8MB**（`sherpa-onnx-pyannote-segmentation-3-0.tar.bz2` 内 `model.onnx`） |

关键事实（写代码前别再查一遍）：
- pyannote segmentation-3.0：输入 `[1,1,160000]`（10s 窗 16k mono fp32），
  输出 `[1,589,7]`，7 类 powerset（∅/{1}/{2}/{3}/{1,2}/{1,3}/{2,3}），帧长 10000/589≈16.98ms，
  单窗上限 3 人、2 人同时说话。
- **每窗的 speaker#1/#2/#3 是局部编号，窗之间不对应**，全局身份仍靠 CAM++ + 聚类。
- 决策理由：抢话是面对面场景的定义性难点，只有 powerset 能表达重叠；
  「VAD 段内找声纹变化点」在混音处失效（叠加向量既不像 A 也不像 B）。
- FireRedVAD 保留做粗筛（抗音乐噪声），角色从「分段」改为「滤区间」。

## 新发现的实现坑

`download_models.py` 是 **HF 专用**（`_get_repo_info` 走 `/api/models/{repo_id}`）。
pyannote 的 ONNX 只在 GitHub release 的 tar.bz2 里，没有可用的非 gated HF 仓库
（pyannote 本体是 torch 权重+gated；`ivrit-ai` 也是 torch；`onnx-community` 是 Transformers.js 导出、
输入签名不同）。→ 需给下载器加「GitHub release + tar.bz2」分支（bz2/tarfile 都在标准库）。

## 实测跑了真实录音，推翻了两处设计（第三次修订，最重要）

样本 `C:\Users\yqz\Downloads\note-3-1795350200989.wav`（16k/mono/16bit，1868s=31.2min），
环境用项目 `.venv`（Py3.11 + onnxruntime 1.24.1 + kaldi_native_fbank 1.22.3 + numpy 1.26.4）。
脚本在 `C:\Users\yqz\AppData\Local\Temp\diarize_test\`（临时目录，未入仓）。
模型取自本机缓存 `C:\Users\yqz\.cache\superting\diarization-models\`
（pyannote seg-3.0 的 `model.onnx`，正是 sherpa-onnx release 那份）；
CAM++ 用中文双语版，从 `hf-mirror.com/csukuangfj/speaker-embedding-models` 下，28.3MB，**192 维**。

### 推翻一：段级嵌入不可用，必须「窗-说话人」级

- 按段嵌入（段长中位 **1.65s**，33.5% <1s）→ 阈值 0.55 出 **67 个簇**，63 个是 1-6 段碎片；
  **相邻段同簇率仅 56.9%**（随机基线 43.2%）。同一人相邻段嵌入互不相似。
- 改 sherpa-onnx 官方做法：对**每个 (10s 窗, 窗内局部说话人)**，把该说话人活动帧的音频
  **首尾相接（丢掉空隙）** 再算一个嵌入，并**排除重叠帧**（`labels*(labels.sum(-1,keepdims)<2)`）。
  有效语音近 10s → 2403 个嵌入 → 段数 531→373，段长中位 1.65→2.87s。

### 推翻二：openwhispr 的阈值会吃掉一个真人

本机校准（同一段录音内测，最可靠）：

```
同一人跨 31 分钟（同簇前半 vs 后半）：质心余弦 0.973   ← 没有观察到漂移
两个不同人（两个主簇）：              质心余弦 0.683
簇内两两 0.78/0.74；跨簇均值 0.519
```

- `MERGE_CENTROID_COS` **0.5 → 0.85**。0.5 会把 0.683 的两个真人并成一个（实测距离阈值 0.55 时确实并了，
  第二大簇 21.7% 被吞掉，单簇变 83.9%）。
- `CLUSTER_DISTANCE_CUT` = **0.40**（距簇内 0.22-0.26 与跨簇 0.48 之间）。
- `LONG_AUDIO_THRESHOLD_DELTA`（openwhispr 的按时长放宽）**移除**，实测无漂移依据。

### 判定「第二簇是真人还是回声副本」的方法（可复用）

两者在聚类结果上长得一样，只有频谱能分：

| 判据 | 真人 | 回声/电话副本 | 本次实测 |
|---|---|---|---|
| 带限 | 低频与 8k 高频俱在 | 明显带限（切低频、高频滚降） | 无带限 → 真人 |
| 中位 RMS | 相近 | 明显更低 | −21.8 vs −22.3 dBFS → 同一通道 |
| 转移矩阵 | 0→1 与 1→0 对称 | 1:1 时间偏移的重复 | `[[264,29],[28,27]]` 对称 |
| 谱质心 | 可差几百 Hz | — | 2952 vs 2193Hz |

结论：**这段录音是 2 个人**（59.1% / 21.7%），不是单人独白。
（我一度误判为单人，因为幽灵过滤后只剩一簇——那是阈值把第二人吞了。）

### 性能实测（原预算 120s/小时，实际 560s/小时）

| 环节 | 31min | 折合 1 小时 |
|---|---|---|
| pyannote 分段 | 62.3s | **120s**（33.5ms/窗，1859 窗） |
| CAM++ 嵌入 | 209.8s | **404s**（87ms/条 × 2403） |
| 聚类+投票+建段 | ~18s | ~35s |

- **批处理实测是反的**（batch1 82.4ms/条 → batch8 134.2ms/条），别按常识去优化这一步。
- 唯一有效杠杆：嵌入用的窗步长从 1s 放到 3s（10s 窗/1s 步长 → 同一音频被嵌入 10 次），
  预计降到 ~200s/小时，但要先量化边界精度损失。

### 最终指标

2 人（59.1% / 21.7%），语音归属 81%，373 段 → 相邻同人合并后 **172 次 ASR 调用**
（中位 5.3s、均值 9.6s、最长 65.7s、**0 次超 Qwen3 的 115s 上限** → 段内不用二次切块）。
重叠帧仅 2.6%，**所以「pyannote 能否切出抢话」本次仍未验证**。
