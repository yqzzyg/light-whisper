# 2026-11-20

## 超长会议录音切片转写（P5）

### 结论先摆

会议录音本来就能录任意长（采集侧 500ms 流式落盘、内存恒定、崩溃可 `repair_header`）。真正的约束在转写：整段交给本地引擎时，Python 端要把整个 WAV 读进内存。现在超过 2 小时的录音自动按 30 分钟切开转写。

### 后端

- 新模块 `services/audio_chunk_service.rs`：`CHUNK_THRESHOLD_SECS = 2h`、`CHUNK_SECS = 30min`、`should_chunk`、`chunk_count`、`snap_to_silence`、`WavChunker`（hound 流式读）、`join_transcripts`。
- `TranscribeRun::run_asr` 分派：`should_chunk && is_local_engine` → `transcribe_in_chunks`；其他情况仍走 `transcription_service::transcribe_file`。
- 每块走 `funasr_service::transcribe_pcm16`（16k 时命中内存协议），**不写临时文件、不 encode WAV**，内存只留「当前块 + 3 秒搜索余量」。
- 新事件 `note-transcription-progress`（`noteId` / `recordingId` / `chunk` / `chunkTotal`），已登记 `formal/verification.json`（163 命令 / 24 事件族）。

### 改回会坏的点

- `silence_radius` 必须 `min(3 秒, samples_per_chunk / 2)`：搜索半径超过块长一半，切点会飘进相邻块。
- 能量打平时必须按「离 target 最近」决胜，否则第一个候选恒胜，切点被拖到搜索区左边界（测试锁的就是这条）。
- `chunkTotal` 是估算值，**不能当循环上界**：静音吸附会让实际块数差一两块。
- 任何一块失败 → 整段失败、不落库。半截转录会让用户以为录音丢了。
- 只有本地引擎切片。在线引擎（GLM 30 秒 / DashScope 约 3.9 分钟）继续由 `check_engine_limit` 整段拦截，别给它开口子。
- 切的是「一段录音内部」，不新增 `note_recordings`、不多写历史。与「用户手动停一下」形成的物理分段是两件事。

### 顺带修掉的既有 bug

`WavAppender::create(&path, sample_rate)` 传的是**采集侧原始采样率**（设备不支持 16k 时是 48k），而 `drain_samples` 写入的一律是重采样后的 16k 数据 —— 那类设备上的录音 header 错标 3 倍，播放变慢、时长算错、转写音调全错。现在固定传 `TARGET_SAMPLE_RATE`。

这个 bug 会直接毁掉切片：hound 按头部 48k 解读，读出的样本数只有实际的 1/3，`should_chunk` 的时长判断也跟着错。

### 前端

- `noteTranscriptionStore` 加 `chunk: { done, total } | null` 与懒订阅。`progressUnsubscribe` 才是「已订阅」标志（沿用 `noteSummaryStore` 的教训，只判 in-flight 标志会在页面反复挂载时重复注册）。
- `NoteEditor` 有 chunk 时用 `notes.transcribingChunk`（「转写中 · 第 3 块 · 已用 02:15」），否则维持原「转写中 · 已用 N」。

### 验证

- 前端：96 文件 / 1045 例；tsc / eslint `--max-warnings=0` / vite build / `check_bundle_budget` 全绿（notes 256KB/300KB，total 589KB/620KB）。
- clippy 新增 0 告警，仍是那 5 条既有（rustc 1.100 新 lint，未动音频/热键路径）。

## P5 第二批：历史反查、重新转写（同日）

### 历史 → 笔记反查

- 新命令 `find_note_by_history(history_id) -> Option<i64>`（`notes_service::find_note_id_by_history`）。
- **必须查两条路径**：`notes.history_id`（历史转存的笔记）与 `note_recordings.history_id`（会议录音的段）。只查前者，会议录音的历史行全部点不动。
- 笔记已删返回 `None`，前端 toast「对应的笔记已被删除」。
- `mode="note"` 的历史行**不再显示「存为笔记」**：转录本就属于某条笔记，再存会造重复笔记（`create_note_from_transcript` 只按 `notes.history_id` 去重，段来源的历史行会漏）。
- `openNoteByHistory` 在打开后要展开目标笔记所在目录，否则侧栏折叠时看不到选中项。

### 重新转写

- `transcribe_note_recording(note_id, force: Option<bool>)`：默认 false 保持原幂等，true 全部重跑覆盖。
- 无录音段的笔记（转录来自历史）force 时**明确报错**，不要静默返回原笔记（用户会以为按钮坏了）。
- **历史行就地更新**（`history_service::update_transcription_result`）：重转 N 次不该堆 N 条历史。段表 `history_id` 只能指向最新一条，旧行会在历史页变成「笔记已删除」死链。单段重转 `transcribe_note_recording_segment` 同样改为就地更新（此前是append）。
- 前端入口在转录 tab 工具栏「重新转写」，仅当 `transcript` 非空且 `recordings.length > 0`；点击前 `window.confirm`，因为它会覆盖手改过的转录。

### 删除二次确认

P5 清单里这条**早已实现**（笔记 / 目录 / 录音段三处都在 `NotesPage` 里 `window.confirm`），我在上一轮只 grep 了 `NotesSidebar.tsx` 就误报「一行确认都没有」。本轮只补强文案：明说录音文件会从磁盘删除。回收站（软删除）仍未做。

## 历史反查补漏：mode 不变的记录（2026-11-20 下午）

用户反馈「上传的录音转成笔记后，历史卡片上没有打开笔记按钮」。原因：上一版只看 `record.mode === "note"`，而上传/听写记录「存为笔记」后 `mode` 仍是 `import` / `dictation`——按 mode 判断永远认不出这类记录已经有笔记。

- 新增 `find_notes_by_history(history_ids: Vec<i64>)`（`notes_service::find_note_ids_by_history`）：整页一次批量反查，返回 `Vec<(history_id, note_id)>`，**顺序跟入参**；先查 `notes.history_id`，未命中的再查 `note_recordings.history_id`；空入参返回空、不报错。
- 判定顺序写死在服务端，前端只管 `noteLinks[record.id]`：有值即 `isNoteRecord`（撤销「存为笔记」），`mode !== "note"` 时额外显示「已转为笔记」角标并换用 `openNoteConvertedHint`（录音仍在历史里，别说成「去笔记里听」）。
- 反查失败只 `console.error`，不能把整个历史列表打成加载失败。
- 反查结果要按本次 ids **先删后加**再合并，否则笔记被删后旧映射还留着，按钮点了会 toast「笔记已删除」。
- 教训：凡是「这个实体是否已关联另一个实体」的判断，都不能靠源记录自带的 mode/状态位，必须查关联表。

## 历史行变死胡同：mode 不能当永久事实（2026-11-20 晚）

现象：历史转笔记 → 删笔记 → 回历史想再转一次，卡片上「存为笔记」和「打开录音所在目录」都没了。

查真实数据（`%APPDATA%\com.light-whisper.app`）：

- `notes.sqlite3` 里仍有 `id=12 title=多喝水 kind=import history_id=48`（10:07 建、10:33 改），说明那条笔记没被删。
- `note_recordings` 里 history 45/47 没有记录 → 那两条 note 模式历史的笔记早就删了。
- history 48 的音频 `1795134531027-1795134512105.wav` 仍在 `history_audio/`；mode=note 的行 `audio_file` 恒为 NULL。

根因两条：

1. `isNoteRecord = mode === "note" || 反查到笔记`——`mode` 被当成永久事实。笔记删掉后这一行永远只剩「打开笔记」死链，再没有转成笔记的入口。
2. mode=note 的行本来就没有历史音频（录音在 `notes_audio/`），删笔记会连录音删掉，所以「打开录音所在目录」从来不存在，不是回归。

修法：

- `noteLookup: Record<id, number | null>` 区分「没查过」与「查过、没有笔记」。`isNoteRecord = noteId != null || (mode === "note" && !looked)`，反查回来即以库为准。
- `openNote` 反查为 null 时当场把该行写成 `null`，卡片立刻变回「存为笔记」。
- 测试：`turns a note-mode row back into a convertible record once its note is gone`、`recovers the convert action after the linked note was deleted elsewhere`。

教训：任何「已关联 X」的判断，`mode`/状态位只能当查询返回前的兜底，最终事实要看关联表；否则关联被删后界面会永久锁死。
