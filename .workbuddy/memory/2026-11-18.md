## Rust 工具链错位（重要，会卡发布）

## 决策：笔记录音默认「先录后转」

用户要求笔记里的会议录音默认先录后转，理由是实时转录耗电。已更新 `docs/notes-feature-plan.md`（§1 需求表、§3.1 现状与耦合点、§3.3 后端清单、§3.4 前端清单、§3.5 会议流、§4 P3/P5、§5 风险、§7 决策 5）。

### 关键代码事实（决定实现路径）
- `start_recording_with_start_owner`（`commands/audio.rs:98`）采集启动后**必定** spawn `spawn_native_recording` 或 `spawn_interim_loop`，没有「只采集」分支；收尾在 `finalize_recording`，绑定字幕/浮层/润色/粘贴/历史，`finalize.rs:288` 注释明确「原生结果不退化为整段 ASR」。→ 笔记录音不能复用听写命令。
- 可复用原语：`spawn_audio_capture_thread(stop_flag, samples, device) -> (JoinHandle, u32)`（`capture.rs:426`，返回设备采样率）；`resample::ResamplerState::push_i16` 增量转 16k；`finalize.rs:968 do_final_asr`（重采样→在线走 WAV / 本地走 `transcribe_pcm16`，已含长音频自适应超时，但私有）；`audio_import.rs:89 transcribe_import_streaming`（1 秒块喂，能出进度，也私有）。
- 方案：新 `services/note_recording_service.rs` 起独立采集会话（`AppState.note_capture` 槽，与听写 `RecordingSlot` 双向互斥），每 30 秒块重采样后追加写 WAV（44 字节占位头、停止回填），内存恒定 2–3MB；停止后整段转写，落 `history(mode="note")` → `notes.transcript`。
- 转写复用需两处小重构：`do_final_asr` 提为 `pub(crate)`；导入的分块喂入循环抽到 service 层共用（约 40 行搬迁，不改行为）。
- 已知限制写进方案：无实时文本（预期管理靠 UI 文案）、1 小时约 3 分钟等待、引擎 `finish` 拼全体 PCM 故建议单次 ≤2 小时（P5 做 30 分钟切片）、在线引擎不适合会议录音。

### 命令登记数修正
原写「12 个新命令」实际是 14（目录 5 + 笔记 6 + 历史转笔记 1 + 摘要 2），加录音 4 个 → **18 命令 + 3 事件**。

### 修订：转写改为「手动按钮 + 复用上传转录接口」

用户提出更简单的形态：笔记里开始只录音 → 停止只存录音文件 → 按钮触发转文字。已按其意见改文档（§1、§3.1 整段转写行、§3.3 拆成「录音只采集」+「转写复用上传接口」、§3.4/3.5/§4 P3 分两阶段、§5 风险、§7 决策 5–7）。

#### 复用可行性核验（代码级）
- `transcribe_imported_audio`（`commands/audio_import.rs:183`）：`import_audio_to_wav` 解码 → `check_engine_limit` → 本地引擎 `transcribe_import_streaming`（1 秒块喂 + finish，推负数 sessionId 的 interim）/ 在线引擎 `transcribe_wav_bytes_dispatched` → `history_service::save_audio` 复制一份 wav → `insert(mode="import", workflow="import")`。
- 障碍只有三处：①命令壳里写死 `mode/workflow="import"` 且会**再复制一份**音频（`save_audio`）；②`transcribe_import_streaming`/`check_engine_limit` 是命令文件私有；③interim 事件只靠 `sessionId<0` 区分，`audioImportStore` 会无条件消费（`interim && sessionId<0`），笔记转写会把文字喂进上传页结果框。
- 解法：拆命令壳与核心（约 50 行搬迁）；录音直接写 `history_audio/{millis}-{seq}.wav`（过 `safe_audio_path`）并让 `HistoryDraft.audio_file` 引用同一文件，**不复制**；interim 事件加 `source` 字段。
- `history_service` GC 只删「被过期历史行引用」的 audio_file（`cleanup_expired_with_connection`），所以未转写的录音不会被 GC 误删，需笔记删除时自行清文件。
- `ensure_reprocessable_workflow`（`commands/history.rs:191`）只放行 `"dictation"`，故 note 记录不支持历史页「重新识别」，重转用笔记自己的按钮。
- 命令总数：14 + 录音 4 + 转写 1 = **19 命令 + 4 事件**。
- 最终不采用 `finalize::do_final_asr`（上一版方案），保留它仅供听写收尾。

### 修订二：转写核心收口为 transcription_service

用户指出 `transcribe_imported_audio` 把「识别 + 保存」揉在一个命令里，复用困难。核实后：`save_audio` 本身已是独立函数，真正的病灶是三点——
1. **引擎分派有三份拷贝**：`commands/history.rs:162 transcribe_wav_bytes_dispatched`（WAV bytes→分派）、`commands/audio_import.rs:89 transcribe_import_streaming`（取锁+1 秒块流式）、`audio_service/finalize.rs:968 do_final_asr`（重采样→分派）；`funasr_service::transcribe_pcm16:732` 是第四层（锁+补零+IPC）。长音频预算/短音频补零/在线上限各写各的。
2. 命令层把「解码 → 校验上限 → 转写 → save_audio → insert 历史」写成一条 saga，转写函数还是命令文件私有。
3. import 的顺序是「先转写后保存（成功才存音频）」，笔记是「先保存后转写」，两者无法共用一个流水线，所以编排必须留在各命令，共享的只能是最底层的转写。

方案（已写入 `docs/notes-feature-plan.md` §3.3「先收口转写核心」+ §4 新增 **P2.5**）：
- 新增 `services/transcription_service.rs`：`transcribe_path(app,state,path,opts)` / `transcribe_pcm(...)`，`TranscribeOptions { progress, on_interim, error_prefix }`，只做「音频→文本」，不落库不写历史。
- 职责切分：识别=transcription_service；音频持久化=save_audio 或录音时落盘；历史=insert（各点自己定 mode/workflow）；编排=命令层 15–30 行。
- 三处旧调用点收敛到它，行为与文案不变；`check_engine_limit` 一起搬入。
- P2.5 纪律：纯搬迁、独立提交、不夹带功能改动；验收=导入 4 单测 + funasr 全量 + 历史重新识别手测 + 37 分钟 wav 复测预算日志不变。
- 文档已改：§3.1 整段转写行、§3.3 三个小节重排（收口→录音只采集→笔记转写）、§3.5 流程图、§4 P2.5/P3、§5 风险行、§7 决策 6。

### 结论修正：不做全量收口，只加「文件 → 文本」窄接口

上一版方案提了 P2.5「把三处分派合成 transcription_service」，审视代码后判定**过度设计**，已从文档删除，改为窄接口方案。

判断依据（读码确认）：
- 三处分派是**三种执行策略**而非误抄：`finalize::do_final_asr`（听写兜底，重采样+一次性）、`audio_import::transcribe_import_streaming`（上传页要 interim 预览）、`history::transcribe_wav_bytes_dispatched`（历史重新识别）。合并成带 `progress/on_interim` 回调的万能函数，只省每处 6 行 match，却把听写与上传两条主流程回归面绑一起。
- 真正可复用的底层件：`funasr_service::transcribe` → `transcribe_wav_bytes_via_path` → `send_command_to_server_for_audio(..., wav_duration_secs)` **已带长音频自适应超时**（上轮修的 37 分钟预算曲线），笔记一次性转写不需要新造超时。
- Python 端 `ServerCommand::Transcribe` 支持 `audio_path`（`qwen3_asr_server.py:245 _load_audio` 用 `os.path.exists` + `_read_mono_audio`），所以可直接传笔记录音路径：不读字节、不写临时文件、不复制音频。
- `history_service::save_audio` 是「复制进 history_audio」；笔记录音本来就在该目录，故用 `HistoryDraft.audio_file` 引用同名字即可，零复制。GC（`cleanup_expired_with_connection`）只删被过期历史行引用的文件，未转写录音安全。

新方案（已写入 §3.3 / §4 P3 / §5 / §7）：
- `services/transcription_service.rs` `transcribe_file(state, app, path, duration_sec, error_prefix)`，本地 → 新增 `funasr_service::transcribe_path`（约 25 行，直接下发 audio_path）；在线 → check_engine_limit（从 audio_import 迁入）+ glm/alibaba。
- `commands/notes.rs::transcribe_note_recording` ≈25 行：取路径 → 转写 → insert(mode="note", audio_file 同文件) → set_transcript。
- `history_service` 需暴露 `reserve_audio_file` / `audio_path` / `delete_audio_if_unreferenced`（三者现在都是私有的）。
- 一次性转写没有块级进度：UI 只显示「已用时 + 预估区间」，不造假进度条；事件减少为 3 个（去掉 note-transcription-progress），命令 19 个。

### 重大修正：笔记音频必须独立目录（history_audio 会被启动清孤儿）

发现上一版方案（沿用「录音写 history_audio、笔记与历史行共用一个文件」）**是错的**。
代码证据：
- `history_service.rs:297-303`（`initialize()` 内）先 `DELETE FROM history_audio_leases`，再 `cleanup_orphan_audio_files_with_connection`（`:810`），后者遍历 `history_audio/` 调 `cleanup_audio_if_unreferenced_with_connection`（`:767`）。
- 该函数只认两个引用来源：`transcription_history.audio_file` 计数、`history_audio_leases` 计数；两者都为 0 就 unlink。
- 租约在启动时被清空 → 租约救不了跨重启。结论：「录完没点转文字就重启」音频会被删。

用户决策：**笔记音频放独立目录 `notes_audio/`**（三选一里选的，另两个是「停止即写 history 占位行」「GC 增加 notes 引用例外」）。

连带调整（已改 `docs/notes-feature-plan.md`）：
- 录音落 `notes_audio/{note_id}-{millis}.wav`；`notes.audio_file` 存名字；转写传绝对路径，零复制。
- 历史行 `audio_file = None`（`HistoryDraft.audio_file` 本就是 `Option<String>`）；`audio_available` 走 `safe_audio_path` 判 false → 历史页无播放按钮，详情标「录音在笔记中」。
- **上传侧改动因此进一步缩小**：`history_service` 完全不动（不需要把 `reserve_audio_file`/`audio_path`/`delete_audio_if_unreferenced` 暴露）。上传侧唯一要改的只剩 `check_engine_limit` 搬迁（`audio_import.rs:149-183` + `:196`，签名 `&[u8]` → `size_bytes: u64`）。
- 新增 `utils/paths.rs::notes_audio_dir()` + `safe_file_in_dir(dir,name)`（把 `safe_audio_path` 的单段名校验抽出共用）。
- 笔记自管回收三处：删笔记、删目录级联、启动扫 `notes_audio/` 未引用残留（崩溃半截录音用 `wav_duration_secs` 的真实剩余裁剪逻辑补写长度）。
